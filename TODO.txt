CRAFTBOX 1.2.0-beta.8 — MANUAL BROWSER TEST CHECKLIST
=====================================================

Covers what beta.8 changes and nothing else. beta.7 closed its own checklist
at 55/55, so everything up to and including that build is already signed off.

Two areas changed:

  A. Build targeting — every loader now installs and tracks the NEWEST build
     upstream publishes for the chosen Minecraft version, rather than the
     newest one on a "stable" channel. On Forge that means the `latest`
     promotion instead of `recommended`. On Paper and Folia it fixes a
     reversed list that was auto-selecting the OLDEST stable build.

  B. Downloads — every download now carries an exact Content-Length, the four
     zip/cbx downloads are packed to a staging file before the response
     begins, and the panel reports packing progress, completion, cancellation
     and refusal over the server WebSocket.

Setup:
  - A fresh container or environment, empty data directory.
  - Enough disk for a second copy of your largest test server: an archive is
    now staged in the OS temp directory before it is sent.
  - Servers to create during the pass: Forge 1.20.1, Paper 1.21.11, Fabric
    (any recent version). A Purpur and a NeoForge server if you have time.
  - One server large enough that packing takes several seconds — drop a few
    hundred MB of junk into its directory if nothing is naturally that big.
    Several checks below are unobservable on a 2 MB server.
  - At least one backup taken, and some event history, on the server you
    export.
  - A browser with its download shelf/manager visible (Chrome's Downloads
    panel, Firefox's Library) — half these checks are about what IT shows.

and substitute below if they have moved on.

  [x] Files tab → "Download Server (.zip)". The browser's download entry

  [x] Files tab → the download button on a single file. Same: real size.
  [x] Mods/Plugins tab → "Download All". Real size.
  [x] Mods/Plugins tab → a single jar's download button. Real size.
  [x] Backups tab → a backup's download button. Real size, and it matches the

  [x] Settings → Export. Real size on the .cbx.
  [x] Public status page → the client mods download. Real size. (No toast

B2. DOWNLOADS — THE PROGRESS TOAST
--------------------------------------------------------------------

Use the deliberately large server for these; a small one settles too fast.

  [x] Starting an export shows a toast that reads "Preparing Server export…"
      and then counts up — "Preparing Server export — 412 MB of 1.1 GB
      (37%)".
  [x] The percentage climbs and does not go backwards or exceed 100%.
  [x] When packing finishes the toast switches to "Downloading Server
      export (1.1 GB)…" and the browser's own download begins at that moment.
  [x] On completion the toast is replaced by a green "Server export
      downloaded (1.1 GB)." and the size agrees with the file on disk.
  [x] Downloading a SMALL file (server.properties) shows no preparing toast
      at all — it is held back 400 ms deliberately so quick downloads do not
      flash one up. A green "server.properties downloaded (1.2 KB)." is still
      expected.
  [x] The page never navigates away during any of this. You stay on the tab
      you started from, scroll position and all.
  [x] Toasts name the right thing: "Server files", "Mods and plugins",
      "Backup archive", "Server export", or the file's own name.

--------------------------------------------------------------------
TESTING NOTES
--------------------------------------------------------------------

Record findings here as they come up, in the style beta.6/beta.7 used:
numbered, with what was expected, what happened, and whether it was resolved
in code or was the checklist being wrong.

Already covered by automated tests before this checklist starts, so treat a
failure in these areas as a surprise rather than an expected gap:

  - Content-Length matching the delivered body exactly, for archives and for
    single files.
  - Packing failures landing before any header is sent (JSON error, not a
    truncated archive).
  - The 507 free-space refusal.
  - Cancellation during packing and mid-transfer, including staging cleanup
    after both.
  - Archive contents round-tripping byte-for-byte.
  - The export archive's layout and manifest.
  - Forge check-upgrade returning 47.4.23 rather than 47.4.10, and Paper
    check-upgrade returning the highest build of the 92 published for
    1.21.11.
  - Every download endpoint's Content-Length, over HTTP, against a real
    instance.

What no automated test can reach, and therefore what this pass is really
for: what the browser's own download UI displays, whether the toasts read
sensibly in sequence, how the packing wait FEELS on a genuinely large
server, and whether any of this behaves differently inside the container.

--------------------------------------------------------------------

1. B7, first bullet — "Start two downloads at once from the same page...
   Both complete, and each toast reports its own file."
   Expected: two independent downloads, each finishing with its own toast.
   Happened: only one ever completes. public/js/download.js drives every
   download through a single shared hidden <iframe> — ensureFrame() returns
   the same element every time, and start(url, label) overwrites its .src on
   each call. Firing a second download while the first is still streaming
   aborts the first mid-transfer at the browser level rather than merely
   confusing the toasts. Confirmed with a server-zip download plus a backup
   download in the same tab (dev instance) and with two concurrent
   /download-zip requests against the built beta.8 Docker image: the toast
   sequence is "Server files A download cancelled." immediately followed by
   "Server files B downloaded (47.0 MB).". The second bullet in B7 ("Start a
   large export in one tab and navigate around in another") is unaffected —
   that's a different browsing context, not a second call into the same
   shared iframe. RESOLVED in code: download.js now gives every in-flight
   download its own frame, drawn from a pool that a frame only rejoins once
   its transfer has terminally settled (complete, cancelled or failed). A
   silence timeout deliberately retires its frame instead of returning it —
   sixty seconds of socket silence does not prove the transfer ended, and
   reusing that frame would abort the very download that went quiet. Re-run
   on the second pass: both downloads complete and each toast names its own
   file.

2. A3, Vanilla bullet — "A Vanilla server still says 'No build tracking for
   this server type.'"
   Expected: that exact message.
   Happened: Vanilla shows "No builds published for this version." instead.
   vanilla.js's getBuilds() always returns null (Vanilla has no build
   concept), so check-upgrade's guard for providers that lack
   getBuilds/getLatestBuild entirely never triggers — the method exists, it
   just returns nothing — and the request falls into the generic "no builds
   available" branch instead of the "no build tracking" one. Checked this
   against the pre-beta.8 code and the behavior is unchanged from beta.7, so
   it predates this release and isn't something beta.8 touched. Leaving
   unresolved as out of scope for this pass; noting because the checklist
   states the wrong expected string, not because anything regressed.

3. B4, "Export with Include backups ticked while a backup is running" bullet.
   Expected: red toast "A backup is currently in progress. Try again when it
   completes."
   Happened: in every real attempt, the export's own live-state check (which
   runs before the backup-lock check that would produce that specific
   message) sees the server already in the `backing_up` state and returns
   the generic "server must be stopped" family of message instead. A real
   backup takes multiple seconds, so by the time an export request arrives
   the state has already flipped; the specific backup-lock message is only
   reachable in a narrow window between backups.js acquiring its lock and
   setOperationalState(BACKING_UP) resolving. Not a regression and not
   blocking — just noting that the checklist's expected wording is very hard
   to actually observe under real timing, so don't read a failure to see it
   as a bug.

4. C, "Create a server, a backup, and a group — all get IDs (uuid)" bullet.
   Expected: groups get a uuid like servers and backups do.
   Happened: servers and backups do get uuidv4 IDs; groups are keyed by name
   instead (src/utils/serverGroups.js stores them as `group_<name>`, with no
   uuid at all). This is by design, not a side effect of the uuid dependency
   bump, so it's the checklist's assumption that's wrong here, not the code.

5. C, final Docker bullet — "pull the published Docker image for this build
   and run the whole of section B against it."
   No image has been published yet for beta.8 (this is a pre-release
   checklist), so a published image doesn't exist to pull. Built the image
   from the repo's own Dockerfile instead and ran it as a real container,
   which is the closest available substitute. The build and run themselves
   were clean — all four Temurin JREs present at the expected paths, native
   modules (better-sqlite3, bcrypt, sharp) compiled and verified in the
   builder stage, and the app starts and serves normally in the runtime
   image. Section B re-run against the live container confirmed exact
   Content-Length, real staging-to-disk in /tmp/craftbox-downloads (watched
   it grow during packing and disappear after), and correct completion
   toasts — all consistent with the non-containerized results. The one
   difference from outside the container was NOTE 1's bug, which reproduces
   identically inside it. (My own build environment for this pass sat behind
   a network proxy that isn't representative of normal Docker hosts and
   needed a one-time workaround to reach the package mirrors at all — that
   is specific to how I ran this test and not something to act on.)
